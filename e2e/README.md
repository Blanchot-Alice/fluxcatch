# Detection E2E

Run the dependency-free Chrome for Testing suite with:

```bash
npm run test:e2e
```

GitHub Actions 在固定的 `macos-14` runner 上运行同一套测试，Chrome for Testing 版本与 `CHROME_PATH` 均由工作流显式固定。CI 先在 fast job 中生成并验证唯一一组 ZIP，再下载该 artifact、解压 extension ZIP，并通过 `FLUXCATCH_EXTENSION_DIR` 与 `FLUXCATCH_EXPECTED_BUILD_COMMIT` 对实际交付内容运行浏览器门槛；browser job 不再重新构建扩展。

Set `CHROME_PATH` when Chrome for Testing is not in the Playwright cache or a standard macOS location. Set `FLUXCATCH_EXPECT_RESTRICTED_POPUP=1` on a screen too short for the popup. The popup follows its content from a 440px floor to a 600px cap, and the one-row fixture popup is expected to sit at that floor, so "shorter than 600px" alone no longer proves a restriction: the real toolbar popup must report a viewport below the 440px floor (or, with more content, clip its list into `#main`), and its body must still match that viewport and keep the footer visible.

To reproduce the packaged-extension boundary locally from a clean checkout:

```bash
npm run package
npm run verify:package
rm -rf /tmp/fluxcatch-packaged-extension
mkdir -p /tmp/fluxcatch-packaged-extension
unzip -q dist/fluxcatch-extension-*.zip -d /tmp/fluxcatch-packaged-extension
FLUXCATCH_EXTENSION_DIR=/tmp/fluxcatch-packaged-extension \
FLUXCATCH_EXPECTED_BUILD_COMMIT="$(git rev-parse --short=12 HEAD)" \
npm run test:e2e
```

## What it checks

The suite targets the v2 surfaces (`extension/ui/v2/README.md` is the API reference). Every UI string it asserts is read from the v2 message modules (`extension/ui/v2/messages/*.js`, through `ui/v2/messages.js`, and `messages/worker.js` for the toolbar tooltip) in the language the run pins: Chrome starts with `--lang=zh-CN` and each audited page stores `zh` under `fluxcatch.uiLanguage.v1`. The modules are imported from `FLUXCATCH_EXTENSION_DIR`, so a packaged run checks the copy it ships. A renamed or deleted message key fails the run instead of silently matching nothing.

The runner creates a fresh profile and loopback fixture server, verifies the runtime extension ID, name and version plus build identity and capability profile, and renders Settings, the popup and the Side Panel at fixed viewports.

- **Settings** (`options/options.html`, 720 × 900 and a 980 × 900 matrix page): ten sections labelled by their headings and listed by the nav in page order (Status, Local engine at `#local-engine`, What FluxCatch can save at `#capabilities`, then Saving, Speed, Finding media, Privacy & network, Notifications, Language & shortcuts and Lab); nav with one current item; the engine in exactly one row, `#row-engine`, the first row of Status with its description line, and Local engine holding only the explanation and the install steps (no setting row, no button); every switch, field, select and text area named by its setting row's `<label for>`; the speed preset as a `role=radiogroup` of radios offering the `form-state.js` presets in order, with the Balanced counts (8 parts / 12 ranges) selecting Balanced and keeping the row's own line, while counts that match no preset check no radio and show the Custom line, and typing the Balanced count back selects Balanced again; the ignore-files field limited to 0 to 100,000 KB on the input and in its line; sign-in info reading "Never stored" with its line; no Save button, save bar or dirty status (v2 autosaves); WCAG 2.5.8 hit areas (24 × 24, counting the switch's hit area) and no button or field below `--control-height-compact`; the 2px field focus ring; Dusk; one column and a non-sticky nav at 390px; no overflow at 125% and 150% effective zoom; the final setting fully visible below the sticky top bar. Stable Settings shows the engine as "Not set up" in the queued (harbour) tone with Set up; the nine capability rows of the stable profile, where everything the engine saves (YouTube included) reads the engine's own "Not set up" until the engine is Ready, live streams and copy-protected video read "Not yet", and video thumbnails read "Yes"; the merging row showing the engine's state; the Instagram/X engine switch off and disabled while the engine is not ready, with "Ask where to save" still enabled; no YouTube, yt-dlp or live-HLS control, no active Lab control except the Developer tools switch, and the home-network switch off.
- **Autosave**: an edit shows the inline Saved, persists in the worker and fades; keyboard insertion of a file-name field autosaves; a failed save (stubbed `SAVE_SETTINGS`) shows `errorText()` on its row, keeps the typed value aria-invalid and unsaved, and stores nothing; out-of-range numbers, an unknown file-name field and invalid domain lines each show their own row reason with the vermilion ring and halo and are never sent.
- **Home network**: turning the switch on asks first in the shared confirm popover (labelled by its question, Cancel focused, Allow tertiary); Enter on Cancel runs it once, returns focus to the switch, and leaves the switch and the stored setting off.
- **Engine row**: deterministic host answers (stubbed `PING_HOST`, `RECOVER_NATIVE_API` and the `nativeMessaging` permission on that page only) are rendered through the page's own Set up and Retry, with the one engine row in view in Status: API binding not ready ("Finishing setup…" with Retry, install steps stay closed), engine missing ("Not installed" with Retry, install steps open with both install commands), and ready (no action and the install steps hidden, merging on, YouTube "Yes" because the host reports a usable yt-dlp, and no raw yt-dlp text anywhere on the page). In each state the merging row and every capability the engine saves show the engine's own word and tone until it is Ready, then "Yes".
- **Popup** (372 × 600 for the in-page audit): BrandMark, the "Download a link" and Settings buttons, Open workspace and All downloads; the Media | Downloads segmented tablist with `data-view`, `aria-controls`, labelled tab panels, click and roving ArrowRight / Home behaviour; the labelled type filter, which describes the list under it (on All types and disabled over the empty Downloads list, usable over the media rows); the empty Downloads view with its sentence ("No downloads yet.") and body line; the list header "Media on this page" (`media.listTitle`) with Rescan and the overflow as its only actions, the overflow holding Download all (two or more items) and the destructive Clear results and closing on Escape; the engine status line "Local engine isn't set up · Set up"; Rescan's busy, disabled, unchanged-label pending state. The real `chrome.action.openPopup` host is measured against `popup.css` (html 372 wide with a 600px cap, body as tall as its content from 440px, `#main` the only scroller): on a roomy screen the popup is between 440 and 600 tall and clips nothing below the cap; overlap and a visible footer are checked in both modes.
- **Side Panel** (420 × 820): the engine line above both lists; list headers, where the media header names the page host only while the list is empty (so not with rows) and carries Rescan, plus the overflow for two or more items; the Downloads header keeping All downloads and hiding Clear finished while nothing has ended, over one body line and no Display sentence; and a tertiary Download named for its media that opens the shared dialog, whose one line states the engine boundary for generic direct media; Cancel closes it and no job is created.
- **Media rows** (popup and Side Panel): a 20px type glyph from `components.js icon()` in the lead, no thumbnail and no chips, one plain meta line. No surface loads a remote image or the fixture's poster (page resource timing plus the fixture server's request count).

The fixture supplies page-derived preview metadata, and the worker still records it on candidates (`remoteThumbnails` stays a profile capability); the surfaces never fetch it. Generic observed direct media is sent directly to the background worker to prove that a fresh profile without native authorization fails closed with `engine_not_set_up`, creates no task and writes no browser file. The suite then clears and binds each detection case to a distinct tab and makes strict assertions for direct media, HLS and DASH detection, including the toolbar tooltip from `worker.action.found`.

Five more cases exercise the site adapters without any engine. Chrome resolves the adapter hostnames (`www.pornhub.com`, `hv-h.phncdn.com`, `missav.ws`, `surrit.com`, `jable.tv`, `cdn.jable-fixture.test`, `www.youtube.com`) to the loopback fixture server through `--host-resolver-rules`, so the content adapters run under their real page hosts while every port stays explicit. The Pornhub page carries a real-shaped `flashvars` object with one signed HLS master per quality and a remote `get_media` entry; the case requires exactly one visible card named after the social-card title, a quality menu of 1080/720/480/240 opaque selectors, the page's own poster, the playing rendition (fetched by the page) merged into that card, and a probe answer that keeps the page's ladder rather than the single variant of the probed master. The MissAV page hides `source='…/playlist.m3u8'` in a p,a,c,k,e,d-packed script produced by the runner's own packer; the case requires the decoded master as the one card, its 1080/720/480/360 renditions from the probe, and the `og:image` preview. The Jable page assigns an AES-128 playlist to `hlsUrl`; the probe must read it as `encrypted` with `aes128` protection and no block. The YouTube watch page must yield one `youtube` row named after the tab title without the site suffix, a probe with an empty ladder (no engine), and a `DOWNLOAD` that fails closed with `engine_not_set_up` and no job. The Economist Insider page sets a session cookie; the fixture's episode API and proxied playlists answer 401 without it, so the case proves the worker reads them with the browser session: one HLS card named by the API, a probe with the 1080/540 ladder and the separate audio rendition, and no signed `u=` token in anything the UI receives.

Before creating any fixture tab, the runner asserts that the home-network setting (`allowPrivateNetworkMedia`, shown as "Allow downloads from my home network") defaults to off and then explicitly enables it only inside the disposable E2E profile. This is required because all fixture traffic uses loopback addresses; the profile is deleted at the end and the product default remains public-network-only.

The HLS fixture mirrors the production-shaped Wistia case rather than using neat same-origin URLs. Its master is requested from a separate `localhost` "fast" host, while five observed rendition URLs use CDN-shaped `/deliveries/` paths and signed-query values that differ from the URLs referenced by the master. The page also requests an `/embed/captions/<id>.m3u8` subtitle playlist and exposes an internal `an_PHRM_…` asset token beside a readable lesson title. The test strictly requires all of that traffic to become exactly one visible video, keeps the fast-host master as its representative, excludes the caption playlist, uses the readable page title rather than the internal token, and preserves all five real quality choices.

The popup flow then opens the master's Download dialog at the popup's `372 × 600` CSS-pixel viewport. The row must be the master (its `data-item-id` and source host), carry Download as its only action, and the dialog must offer the automatic best quality plus five renditions labelled by height (opaque selectors only), derive the row title and the filename from the readable page title, offer `MP3 · 仅音频` as a normal output format that switches the extension and hides quality, hold only the link, file name, format and quality fields (no checkbox, no concurrency input), and show "Local engine isn't set up · Set up" as its one line. As in v1, the dialog must be geometrically centred on both axes (within 2 CSS pixels) and lie fully inside the viewport; the v2 dialog contract adds that its body scrolls and its sticky action row (Cancel, then the one primary Download) is inside the dialog and not covered at either button's centre. Escape closes it as a cancel and returns focus to the row's Download. A second popup flow double-clicks Download on a slow master: the row and its Download turn aria-busy (the button stays enabled by design), the row's meta line reads "Reading qualities…", and exactly one manifest request reaches the server before the dialog opens.

Failures, missing browser binaries, timeouts, duplicate candidates, caption false positives, internal-token filenames, off-centre dialogs, a clipped or covered dialog action row, missing controls and missing message keys return a non-zero exit code.

The latest local JSON result is written to `e2e/artifacts/latest.json` (schema 4), with UI screenshots under `e2e/artifacts/screenshots/` and the visual matrix under `e2e/artifacts/phase-b-matrix/` (DPR 2, captured once the pond layer has settled, as the design audit captures; the report states the extension directory and the commit through `scripts/lib/build-identity.mjs`, the same identity the audit stamps); machine-specific paths are redacted, and artifacts and temporary profiles are ignored by Git. A complete 0.2.5 run contains 8 detection cases, 3 UI pages, 3 interaction flows, and 15 deterministic visual states, in this order: `options-light-980x900`, `options-dark-980x900`, `options-narrow-390x844`, `options-autosaved`, `options-validation`, `options-private-network-confirm`, `options-engine-api-unavailable`, `options-native-host-missing`, `options-native-host-ready`, `reduced-motion`, `popup-372x600`, `sidepanel-420x820`, `sidepanel-download-dialog`, `popup-manifest-loading`, `download-dialog`.

## Evidence boundary

This suite validates generic detection, token-insensitive cross-host master/rendition grouping, subtitle-playlist exclusion, runtime build/profile identity, stable capability rows and glyph-only media rows, the popup HLS download dialog and its fit in 372 × 600, the generic native-authorization fail-closed boundary, Settings autosave and validation, direct rendering of the three extension pages, and manifest-loading behaviour. `localhost` and `127.0.0.1` stand in for separate fast/CDN hosts; this proves relation logic against the fixture shape, not production DNS behaviour. The engine rows are driven by stubbed worker answers on one Settings page, so they prove the page's rendering of each host state, not a real native host. Directly opening the Side Panel document does not validate Chrome's surrounding Side Panel shell or a manual toolbar-open gesture. The Downloads page (`extension/downloads/`) and the component preview are not exercised here; their unit tests cover them. The popup and Side Panel audits run on a profile with no downloads, so job rows (live-row meta, the Cancel confirmation and its wording, relative times, the segment map or parts line) and the media empty states with their Rescan are not exercised here either. The suite does not yet exercise full Bilibili/Instagram/X adapter journeys, including real SPA navigation, worker-restart restoration, the default strict Instagram/X Chrome route, the `useNativeForDirect=true` Native override, `saveAs` isolation, or saved-byte assertions; those capabilities remain adapter beta. The site-adapter cases prove detection, grouping, titles, probes and the engine gate against fixture pages; they do not run yt-dlp or the native host, so the brokered YouTube transfer, the Pornhub/MissAV header replay and the Jable key fetch are covered by the host's own unit tests (`native-host/tests`) and the worker smoke test, not here. Real Cloudflare challenges are out of scope. It also does not establish native-host installation, HLS/DASH output validity, Range concurrency, public-network throughput, task-list session semantics, or compatibility with arbitrary websites. Those require separate native download fixtures and performance benchmarks with request-level server telemetry.
