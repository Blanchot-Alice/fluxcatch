# Privacy Policy

Effective date: 2026-10-25

Havre processes media information on the user's device to provide its single purpose: detecting media requested by the current page and saving a resource selected by the user.

## Data processed

Havre may process:

- page URL and title;
- media resource URLs, MIME types, dimensions, duration, codecs, size, and response metadata;
- short-lived request headers needed to repeat a selected media request, limited to `Accept`, `Authorization`, `Cookie`, `Origin`, `Referer`, and `User-Agent`;
- extension settings and download options;
- redacted local download status and error messages for the current browser session.

## How data is used

This data is used only to show detected media, inspect a selected manifest, repeat a user-selected request, and save the resulting file. Havre does not use browsing activity or authentication data for advertising, profiling, credit decisions, or unrelated analytics.

## Storage and retention

- Candidate metadata with credential-free display URLs may be stored in Chrome session storage and is removed when the relevant tab state is cleared or the browser session ends. Only explicitly allowlisted, non-secret page identity parameters (such as Bilibili's page number) may remain. Media resource candidates with other query parameters, plus separately modelled signed Bilibili track URLs, stay only in service-worker memory rather than being persisted; after suspension they require later trusted playback traffic or an explicit rescan to be rediscovered.
- Settings are stored in Chrome local extension storage until changed or the extension is removed.
- Captured request headers remain only in service-worker memory, are bounded, and expire after at most five minutes; the service worker removes a selected capture earlier when its native task ends. They are not written to extension storage.
- On a supported Bilibili `/video/` page, the **自动补全站点画质** setting is enabled by default. This default is an explicit product decision: automatic completion is needed so the toolbar badge reflects the available media qualities after trusted playback or preload without requiring the user to open Havre and scan again; users can turn it off at any time. After the page makes its first trusted Bilibili media request (which may result from playback or player preload), Havre may request Bilibili's page-list and playback metadata with the browser's existing bilibili.com cookies so a logged-in user sees the qualities their account can play. Repeated Range/preload signals share one in-flight request; successful discovery is cached for 45 seconds and a failed automatic attempt waits at least five seconds before retrying. Page completion and merely opening or closing the popup or Side Panel do not start this request. Turning the setting off prevents every automatic metadata request, including the trusted-playback path; an explicit **重新扫描** remains available. These fixed adapter requests go only to `api.bilibili.com`; no credentials are sent elsewhere. Signed video/audio track addresses remain only in service-worker memory for at most two minutes; the popup, Side Panel, broadcasts, and Chrome session storage receive only redacted track metadata and opaque quality selectors. Bangumi pages are not currently claimed as supported.
- On supported top-level Instagram and X pages, bounded page-world observers clone eligible JSON fetch/XHR responses without consuming or modifying the page's originals. They inspect at most 4 MiB (Instagram) or 8 MiB (X), traverse bounded object counts/depths, and publish only one validated complete Instagram MP4 rendition or validated `video.twimg.com` MP4 metadata. Inline payload scanning remains bounded and current-shortcode constrained where applicable. Full response bodies and unrelated page content never leave the page world. Signed media URLs remain memory-only; the isolated content script may keep at most 256 page-scoped entries for 15 minutes so a still-open tab can restore them after MV3 worker suspension, but they are never written to extension storage.
- On a YouTube watch page the GitHub build shows one card for the page itself; ordinary media detection stays off YouTube. Reading that card's qualities or saving it sends only the canonical watch address (`https://www.youtube.com/watch?v=…`) to the local engine, with no cookies or other request headers. The engine runs the copy of yt-dlp already installed on this computer, with its user configuration and cache turned off, and every connection yt-dlp opens passes through the engine's loopback broker, which applies the same network policy as every other native transfer. yt-dlp then contacts YouTube's servers directly from this computer. Havre does not bundle yt-dlp; without it, no request is made to YouTube.
- A paused task keeps a resume recipe in Chrome session storage: the tab id, the media kind, a SHA-256 digest of the media key, the options the user chose and the output file name. The media address itself is not stored; resuming re-finds the address among the page's current candidates by digest. The local engine keeps the paused part file with its checkpoint, or the staged segments with a small marker that names the work directory and carries a digest of the playlist address; both are removed when the task is cancelled or resumed to completion, and expire after a week.
- A pasted download address is treated exactly like a detected candidate of the current tab: it is kept in Chrome session storage under the same rules, the engine receives it with no cookies or page headers, and the type probe that precedes it sends no credentials.
- The save location you choose, and the folders chosen before it, are stored by the local engine in `~/Library/Application Support/Havre/config.json` on this computer only. The engine's Finder actions stay confined to those folders.
- Download-task snapshots use an explicit field allowlist in Chrome session storage, are capped at 200 entries, omit media URLs/headers/manifests/output paths, and redact credentials, query strings, and local paths from status text.
- When the extension must reload itself once to obtain Chrome's native-messaging binding after the permission is granted, it copies the session-storage items above (persisted candidates, previews, task snapshots) together with the requested download's credential-free address and options into Chrome local extension storage for the hand-over. The replacement worker replays that copy once, immediately drops it, and keeps only a timestamp for the five-minute cooldown; a copy older than two minutes is discarded unread.
- The download history (`下载记录`) keeps ended tasks in Chrome local extension storage on this computer only: file name, size, status, the source page's title and credential-free URL, media facts reported by the local engine (duration, resolution, container, codecs), a small poster frame rendered locally by FFmpeg, and, for engine-saved files, the published path inside the engine's download folder. The path is used only to drive the Finder actions (open, reveal, move to Trash, existence check) and is never included in popup, Side Panel or downloads-page payloads; only the engine's download folder itself is shown. The history is capped at 400 records (poster frames for the most recent 120), can be cleared or pruned record by record from the downloads page, and is removed with the extension's storage. The local engine accepts file actions only for regular files inside its own download folder.
- During native-owned transfers, `Cookie`, `Authorization`, `Origin`, and `Referer` headers are removed when a redirect or manifest-introduced child crosses origins. Once removed, they are not restored later in that request lineage.
- The user-triggered **复制诊断信息** action contains only allowlisted extension/native version, build, protocol, compatibility, FFmpeg-availability, and capability-profile fields. It excludes page or media URLs, titles, request headers, credentials, and local paths.
- The separately installed native host, required for most save actions but not detection, receives only the headers and URL needed for the download the user starts. Version-2 resume checkpoints store SHA-256 digests of the URL and entity validators, plus byte length and completed ranges; they do not store the URL, path, query, fragment, raw validator values, Cookie, Authorization value, or other request headers.
- Downloaded files remain on the device until the user deletes them.

## Data sharing and network services

Havre has no developer-operated telemetry, advertising, analytics, account, or cloud-sync service. Passive detection observes the page's own requests. With default-on automatic quality enrichment, a supported site's first trusted media request (playback or preload) may call only that site's fixed page-list and playback-metadata endpoints with same-site credentials, subject to the in-flight, 45-second success-TTL, and five-second failure-cooldown limits above. Turning the setting off blocks all such automatic calls; an explicit rescan or user-selected download may still contact the relevant source service. Page completion and merely opening or closing Havre remain read-only. Control messages to the native host stay on the same device.

Havre-owned active fetches default to public targets. Extension-owned manifest probes validate literal URL/host information, purpose, provenance, and worker-derived origin allowlists and reject redirects; they do not resolve DNS or inspect connected peers. To show a card's poster, the GitHub build may request the image the page itself names (its video poster or social-card image) without cookies or a referrer, without following redirects, as a raster image of at most 8 MiB, and only from the page's own site, the hosts its media came from, or a site adapter's fixed image hosts; when that fails, the card shows packaged media-type artwork. The native engine separately validates DNS answers, pins the connected peer, rechecks redirects and manifest children, and protects against rebinding. Users may explicitly enable local-network media for devices they control; cloud metadata and reserved network ranges remain blocked even then. A generic final media response observed by Chrome is still transferred through the native policy broker; the local-network opt-in expands only that broker's allowed target class and does not switch to an unpinned browser transfer. Chrome-backed saving is limited to a complete Instagram/X MP4 whose provenance, top-level page origin, scheme, exact CDN host, media type, and fragment-free form pass the fixed adapter allowlist. Chrome owns only that narrow transfer lifecycle. Enabling **可信直链也使用本地下载引擎** sends even those eligible files through the native broker; Chrome's save-location prompt then does not apply to that transfer.

Havre does not sell user data. When automatic supported-site quality enrichment is enabled, it may send the current site's existing credentials only to that site's fixed page-list and playback-metadata endpoints as described above. For an explicit inspect or download action, it may send the minimum required request data to the relevant source resource server. It makes no other developer-directed third-party transfer.

## User controls

Users can disable automatic supported-site quality enrichment, require eligible trusted Instagram/X files to use the native engine, clear detected items from the popup, clear completed session tasks from the Side Panel, remove single records or the whole download history from the downloads page, decline or disable completion notifications (the optional browser permission is requested only from an explicit button), remove the native host, clear extension storage, uninstall the extension, and delete downloaded files using operating-system controls or the history's move-to-Trash action.

## Protected and restricted content

Havre does not decrypt DRM-protected media or bypass paywalls, access controls, or login systems. Version 0.3.0 is a development/GitHub candidate; a future Store artifact must physically enforce the capabilities accepted for that listing.

## Limited Use

Havre's use of information received from Chrome APIs is limited to providing and improving the extension's user-facing single purpose. The data is not used for personalized advertising, is not made available for human review except when the user deliberately includes it in a support report, and is not transferred for unrelated purposes.

## Contact

Privacy questions can be filed through the public repository's issue tracker without attaching private URLs, cookies, authorization headers, or downloaded media.
